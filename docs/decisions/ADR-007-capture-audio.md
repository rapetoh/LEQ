# ADR-007: Audio capture stack for attempts and for the debate

Status: proposed (Phase 0 desk spike, to be confirmed on real devices in Phase 1)
Date: 2026-09-06
Deciders: Roch (owner), with the Phase 1 device checklist below as the gate

## Context

LEQ needs two different audio paths on the phone:

- (a) Daily attempts (`tentatives`): a 60 to 300 s recording, uploaded as one file to the private bucket `audio-tentatives` at `{utilisateur_id}/{id}.m4a` (see `docs/DATA-MODEL.md`). The worker decodes it to PCM and `packages/moteur` plus the Praat CLI compute volume (`volume.moyen_db`, `volume.ecart_type_db`, `volume.chutes_fin_phrase`) and pitch (`hauteur.*`). These measures are only meaningful if the phone does not apply automatic gain control (AGC), noise suppression or dynamics processing before encoding. Sample rate 16 kHz mono is enough for speech measures and is what every STT provider wants.
- (b) The debate (face-à-face, Phase 8): the user speaks, the audio is streamed to `apps/serveur` (`temps-reel` process group) for streaming STT, Claude answers as Rétor, and TTS audio comes back as PCM chunks that must start playing quickly. Target: under 2 s per turn. The debate debrief is built from the transcript only (plan, Phase 8), so acoustic fidelity does not matter there, but latency and a working duplex path do.

Constraints from the plan (`~/.claude/plans/rippling-marinating-peacock.md`): Expo SDK 57 with Continuous Native Generation (CNG) and config plugins, New Architecture only (mandatory since SDK 55), one codebase for iOS and Android, no local Android SDK on the development Mac (Android is verified through EAS builds on a physical device), and store binaries built on EAS.

Version facts checked on 2026-09-06:

- Expo SDK 57 was released on 2026-06-30. The `sdk-57` branch template pins `expo ~57.0.20`, `react 19.2.3`, `react-native 0.86.3` (https://github.com/expo/expo/blob/sdk-57/templates/expo-template-bare-minimum/package.json). The plan says React Native 0.87; the SDK 57 template says 0.86.3. This is recorded as an open point below.
- `expo-audio` on the `sdk-57` branch is `57.0.4` (2026-08-20).
- `react-native-audio-api` latest stable is `0.13.3` (2026-08-17); `main` is at `1.0.0` with nightlies (`1.0.0-nightly-*`).

## Options considered

### Option 1: `expo-audio` 57.0.4 (first party)

Sources: https://docs.expo.dev/versions/v57.0.0/sdk/audio/ , https://github.com/expo/expo/tree/sdk-57/packages/expo-audio (files `src/Audio.types.ts`, `src/AudioStream.types.ts`, `ios/AudioRecorder.swift`, `ios/AudioStream.swift`, `ios/AudioModule.swift`, `android/src/main/java/expo/modules/audio/AudioRecorder.kt`, `AudioStream.kt`, `AudioRecords.kt`, `AudioModule.kt`), https://github.com/expo/expo/blob/sdk-57/packages/expo-audio/CHANGELOG.md

File recording (`AudioRecorder`, `useAudioRecorder`, `prepareToRecordAsync`, `record`, `pause`, `stop`, `getStatus`):

- `RecordingOptions`: `extension`, `sampleRate`, `numberOfChannels`, `bitRate`, `isMeteringEnabled`, `directory` (`'cache' | 'document'`), `fileName`. `RecordingPresets.HIGH_QUALITY` is `.m4a`, 44100 Hz, stereo, 128 kbps; `LOW_QUALITY` is 64 kbps. A custom preset at 16000 Hz, 1 channel, 64000 bps is allowed.
- Android (`RecordingOptionsAndroid`): `outputFormat` in `'default' | '3gp' | 'mpeg4' | 'amrnb' | 'amrwb' | 'aac_adts' | 'mpeg2ts' | 'webm'`, `audioEncoder` in `'default' | 'amr_nb' | 'amr_wb' | 'aac' | 'he_aac' | 'aac_eld'`, `maxFileSize`, and `audioSource` (`RecordingSource`) in `'camcorder' | 'default' | 'mic' | 'remote_submix' | 'unprocessed' | 'voice_communication' | 'voice_performance' | 'voice_recognition'`. `AudioRecords.kt` maps these one to one to `MediaRecorder.AudioSource.*`, so `UNPROCESSED` and `VOICE_RECOGNITION` are both reachable. Implementation is `android.media.MediaRecorder`.
- iOS (`RecordingOptionsIos`): `outputFormat` (`IOSOutputFormat`, for example `MPEG4AAC`, `LINEARPCM`), `audioQuality` (`AudioQuality.MIN` to `MAX`), `bitRateStrategy`, `linearPCMBitDepth`, `linearPCMIsBigEndian`, `linearPCMIsFloat`. Implementation is `AVAudioRecorder`.
- Audio session on iOS: `AudioRecorder.swift` calls `session.setCategory(.playAndRecord, mode: .default, options: sessionOptions)` inside `prepareToRecordAsync`, and `AudioModule.swift` `setAudioModeAsync` always calls `setCategory(category, mode: .default)`. There is no option to select `AVAudioSession.Mode.measurement`. Apple documents that `.measurement` is the mode that minimises system-supplied signal processing and "disables some dynamics processing on input and output signals" (https://developer.apple.com/documentation/avfaudio/avaudiosession/mode-swift.struct/measurement). So with `expo-audio`, iOS input keeps the default dynamics processing. Android AGC can be avoided with `audioSource: 'unprocessed'` (which "behaves like DEFAULT otherwise" when the device does not support it, https://developer.android.com/reference/android/media/MediaRecorder.AudioSource) or `'voice_recognition'`.
- Metering: `isMeteringEnabled` gives `RecorderState.metering` in dB (`averagePower(forChannel: 0)` on iOS, `20 * log10(maxAmplitude / 32767)` on Android).
- Interruptions: on iOS, `AudioModule.swift` observes `AVAudioSession.interruptionNotification`; on `.began` it calls `recorder.pauseRecording()` for every recording recorder; on `.ended` it reactivates the session and resumes players only, never recorders. The file stays valid (AVAudioRecorder pause), but JavaScript must decide to resume or stop. On Android, `AudioModule.kt` requests audio focus and reacts to focus changes for players and playlists only; recorders get no focus handling and there is no telephony listener. What `MediaRecorder` produces during a phone call is device dependent and must be measured.
- App kill on Android: `MediaRecorder` with `MPEG_4` writes the `moov` atom when `stop()` is called. If the process is killed mid-recording the file has no `moov` atom and is unplayable (Android docs on `stop()`: the output file "is not properly constructed" when the recorder is not stopped correctly, https://developer.android.com/reference/android/media/MediaRecorder ; background on the moov atom: https://ffmpeg-cookbook.com/en/articles/moov-atom/). `expo-audio` has no recovery for this. The same holds for `AVAudioRecorder` M4A on iOS.
- Background recording: `setAudioModeAsync({ allowsBackgroundRecording: true })` plus the config plugin option `enableBackgroundRecording` (adds `UIBackgroundModes: audio` on iOS and a foreground service with a "Recording audio" notification on Android). Added in 55.0.0.
- Live PCM to JavaScript: `useAudioStream(options)` and the `AudioStream` class (added in 56.0.0, PR expo/expo#44902). `AudioStreamOptions`: `sampleRate` (default 48000), `channels` (default 1), `encoding` (`'float32' | 'int16'`), `onBuffer(buffer: AudioStreamBuffer)` with `data: ArrayBuffer`, `sampleRate`, `channels`, `timestamp`. Both platforms deliver about 100 ms buffers (`bufferSize = sampleRate * 0.1` on iOS, `DEFAULT_BUFFER_DURATION_MS = 100` on Android). On iOS `AudioStream.swift` forces `session.setCategory(.record, mode: .measurement)` on `start()` and deactivates the session on `stop()`: raw input, but the `.record` category makes simultaneous playback impossible. On Android `AudioStream.kt` opens `AudioRecord(MediaRecorder.AudioSource.MIC, ...)` with no way to choose `UNPROCESSED` or `VOICE_RECOGNITION`. In 57.0.x the stream has only `start()` and `stop()`; `startFileRecordingAsync` / `stopFileRecordingAsync` (WAV or raw PCM file written from the stream) exist only in the unpublished changelog on `main` and will ship with a later SDK.
- PCM playback: none. `AudioPlayer` plays files and URLs. There is no API to enqueue PCM chunks. `useAudioSampleListener` is a player-side waveform tap, not an input.

Verdict: good enough first-party file recorder with Android raw sources, but no iOS measurement mode, no interruption handling for Android recorders, no PCM playback, and a streaming API that cannot coexist with playback on iOS. It cannot cover the debate.

### Option 2: `react-native-audio-api` 0.13.3 (Software Mansion)

Sources: https://github.com/software-mansion/react-native-audio-api (836 stars, 42 open issues, pushed 2026-09-04, MIT), https://docs.swmansion.com/react-native-audio-api/docs/inputs/audio-recorder/ , https://docs.swmansion.com/react-native-audio-api/docs/system/audio-manager/ , https://docs.swmansion.com/react-native-audio-api/docs/sources/audio-buffer-queue-source-node/ , https://docs.swmansion.com/react-native-audio-api/docs/other/compatibility/ , https://docs.swmansion.com/react-native-audio-api/docs/other/runtime-flags/ , https://github.com/software-mansion/react-native-audio-api/releases , https://github.com/software-mansion/react-native-audio-api/blob/main/THIRD_PARTY.md

- Maintenance: monthly releases through 2026 (0.11.5 on 2026-02-16 up to 0.13.3 on 2026-08-17), `1.0.0` in progress on `main` with nightlies (`audio-api-nightly` dist tag). Peer dependencies `react: *`, `react-native: *`, optional `react-native-worklets >= 0.6.0`. Codegen config present (`rnaudioapi`, TurboModule). The published compatibility table lists 0.12.x for React Native 0.76 to 0.85 on the New Architecture and does not yet list 0.13.x or 0.86; the repository's example app on `main` runs React Native 0.87.0. Support for RN 0.86.3 (SDK 57) is therefore likely but unverified: item 1 of the checklist.
- Expo: config plugin `react-native-audio-api` with `iosBackgroundMode`, `iosMicrophonePermission`, `androidPermissions`, `androidForegroundService`, `androidFSTypes`. Development build required (no Expo Go). Defaults in 0.13.3 target playback (`FOREGROUND_SERVICE_MEDIA_PLAYBACK`, `androidFSTypes: ['mediaPlayback']`); for background recording on Android 14+ the app must add `android.permission.RECORD_AUDIO`, `android.permission.FOREGROUND_SERVICE_MICROPHONE` and the `microphone` service type through the same options.
- Input (`AudioRecorder`, one instance per app): `onAudioReady({ sampleRate, bufferLength, channelCount }, ({ buffer, numFrames, when }) => ...)` delivers Float32 PCM in [-1, 1] at the requested rate (native resampling); the documented example uses `sampleRate: 16000`, `bufferLength: 1600` (100 ms), `channelCount: 1`. `enableFileOutput({ format, preset, channelCount, directory, subDirectory, fileNamePrefix, rotateIntervalBytes, androidFlushIntervalMs })` with `FileFormat.Wav | Caf | M4A | Flac` and `FilePresetType { bitRate, sampleRate, bitDepth, iosQuality, flacCompressionLevel }`; `start()`, `pause()`, `resume()`, `stop()` returning `FileInfo { paths, size, duration }`. Both modes can run at once (file plus callback). `connect(context, destination)` puts the microphone into the audio graph through `RecorderAdapterNode`.
- Capture chain: Android uses Oboe with `SharingMode::Exclusive`, `Float` format, and in 0.13.3 the input preset is fixed to `InputPreset::VoiceRecognition` (no AEC, no AGC on the standard chain). The option `androidInputPreset` (`'generic' | 'camcorder' | 'voiceRecognition' | 'voiceCommunication' | 'unprocessed' | 'voicePerformance'`) and `iosVoiceProcessing` (AEC, NS, AGC through Apple's voice-processing I/O, default `false`, "keeps the raw microphone signal") were merged on 2026-08-18 (PR #1210) and are only in the nightlies, not in 0.13.3. iOS uses `AVAudioEngine`; `AudioEngine.mm` on 0.13.3 never calls `setVoiceProcessingEnabled`, so input is raw at the engine level.
- Audio session: `AudioManager.setAudioSessionOptions({ iosCategory, iosMode, iosOptions })` with `iosCategory` in `'ambient' | 'multiRoute' | 'playAndRecord' | 'playback' | 'record' | 'soloAmbient'`, `iosMode` including `'measurement'`, `'voiceChat'`, `'spokenAudio'`, `'default'`, and `iosOptions` including `'defaultToSpeaker'`, `'allowBluetoothHFP'`, `'allowBluetoothA2DP'`, `'mixWithOthers'`, `'duckOthers'`, `'overrideMutedMicrophoneInterruption'`. `setAudioSessionActivity(true | false)`, `observeAudioInterruptions(enabled, focusType?)` with events `{ type: 'began' | 'ended', shouldResume }`, `observeVolumeChanges`, `requestRecordingPermissions()`, `getDevicePreferredSampleRate()`. The string `"measurement"` is mapped in `AudioSessionManager.mm` at 0.13.3.
- Output: `AudioContext` (Oboe `PerformanceMode::LowLatency` on Android, `AVAudioEngine` on iOS). `createBufferQueueSource({ pitchCorrection })` gives `AudioBufferQueueSourceNode` (mobile only) with `enqueueBuffer(buffer: AudioBuffer): bufferId`, `dequeueBuffer`, `clearBuffers`, `start(when?, offset?)`, `pause()`, `stop()`, `onBufferEnded({ bufferId, isLastBufferInQueue })`. Buffers are built with `context.createBuffer(1, length, sampleRate)` and `copyToChannel(float32Array, 0)`. That is exactly the "play PCM chunks as they arrive" primitive the debate needs. Also `StreamerNode` for HLS (not needed).
- Licence: MIT for the library; WebKit-derived code under BSD; FFmpeg (`libavcodec`, `libavformat`, `libavutil`, `libswresample`) under LGPL 2.1+, shipped as prebuilt dynamic binaries downloaded at install time. FFmpeg is optional: `disableFFmpeg: true` in the config plugin, `ENV['DISABLE_AUDIOAPI_FFMPEG'] = '1'` in the Podfile, `disableAudioapiFFmpeg=true` in `gradle.properties`. Without FFmpeg, Android file output is WAV only (iOS uses AVFoundation for all formats), and remote URL streaming and HLS are unavailable. `isFfmpegEnabled()` reports the build state. Issue #1173 (open) is about FFmpeg headers leaking into the npm artifact when FFmpeg is disabled.
- Known open issues relevant to us: #1220 (iOS, 0.13.2: recording never resumes after an interruption because `onInterruptionEnd` restarts the engine without reactivating the session; reporter patched it locally), #1254 (Android: platform AEC does not cancel the app's own playback unless the output stream also uses `Usage::VoiceCommunication`), #1266 (iOS overnight background audio memory growth), #464 (echo cancellation for concurrent recording and playback, feature request).

Verdict: the only candidate that covers both paths with one audio session owner, sets `.measurement` on iOS, records to M4A or WAV, streams Float32 PCM in, and plays PCM chunks out with a low-latency engine. Costs: a third-party native dependency with prebuilt binaries, FFmpeg licensing to handle, `androidInputPreset` still nightly-only, and RN 0.86 support to prove.

## Decision

1. Attempts and debate both use `react-native-audio-api`, pinned to `0.13.3` in `apps/mobile`, added through its config plugin under CNG. It is the single owner of the audio session on the phone. `expo-audio` is not installed in Phase 1. If a later phase needs it (for example lock-screen playback of a workshop recording), it must not be loaded on a screen that records, because its `AudioModule` registers its own `AVAudioSession` observers and sets the category to `.playAndRecord` with mode `.default` on every `prepareToRecordAsync`.

2. Attempts (path a):
   - Session: `AudioManager.setAudioSessionOptions({ iosCategory: 'record', iosMode: 'measurement', iosOptions: [] })` before `setAudioSessionActivity(true)`. `'record'` rather than `'playAndRecord'` because no sound is played during a take, and Bluetooth HFP input is not offered (`allowBluetoothHFP` omitted) so that the sample rate stays at the built-in microphone's rate.
   - Recorder: one `AudioRecorder`, `enableFileOutput({ format: FileFormat.M4A, channelCount: 1, preset: { sampleRate: 16000, bitRate: 64000, bitDepth: 16, iosQuality: IOSAudioQuality.High } })` on iOS. On Android the default is the same M4A through FFmpeg; the Phase 1 checklist decides whether FFmpeg stays in the Android build (see Consequences). File goes to `directory: 'cache'` under a subdirectory excluded from backups, named by the client-generated `tentatives.id`.
   - Android input preset: `voiceRecognition` (the 0.13.3 default, no AEC or AGC on the standard chain). When `1.0.0` ships, switch to `new AudioRecorder({ androidInputPreset: 'unprocessed' })`, which Android falls back to the default source when the device lacks `PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED`.
   - Metering for the on-screen level indicator comes from `onAudioReady` with `sampleRate: 16000`, `bufferLength: 1600`, `channelCount: 1` (RMS computed in JavaScript), not from a separate metering API.
   - Interruptions: `AudioManager.observeAudioInterruptions(true)`. On `began` the take is ended (`stop()`), the file is kept only if it is at least `duree_diagnostic_min_s` long, and the UI shows the X-state for an interrupted take. We do not try to resume across a phone call: a paused and resumed take would have a hole that corrupts `debit.fenetres` and `silences`.
   - App kill: the local queue marks a take `enregistrement` when `start()` resolves and moves it to `en attente réseau` only after `stop()` has returned a `FileInfo` with `duration > 0`. A file whose state is still `enregistrement` at next launch is deleted, never uploaded. This makes the missing `moov` atom a lost take, not a corrupt upload. `rotateIntervalBytes` is not used in v1 (the docs warn of audible joins for M4A segments).
   - Background: `iosBackgroundMode: true` and the Android foreground service with the `microphone` type, so a locked screen does not cut a take.

3. Debate (path b):
   - Session: `setAudioSessionOptions({ iosCategory: 'playAndRecord', iosMode: 'voiceChat', iosOptions: ['defaultToSpeaker', 'allowBluetoothHFP'] })`. `voiceChat` engages Apple's voice processing (echo cancellation, AGC), which is acceptable here because the debate is scored on the transcript only.
   - Uplink: the same `AudioRecorder`, `onAudioReady({ sampleRate: 16000, bufferLength: 1600, channelCount: 1 })`, Float32 converted to Int16 little-endian in JavaScript (or in a worklet, `react-native-worklets >= 0.6.0` is an optional peer) and sent as binary WebSocket frames to `temps-reel`, which forwards them to the streaming `Transcripteur`.
   - Downlink: one `AudioContext({ sampleRate: <TTS rate, 24000 expected> })`, one `createBufferQueueSource({ pitchCorrection: false })` connected to `context.destination`. Each TTS PCM chunk from the server (Int16, 200 to 500 ms) becomes `context.createBuffer(1, frames, rate)` plus `copyToChannel`, then `enqueueBuffer`. `onBufferEnded` with `isLastBufferInQueue` drives the "Rétor has finished" state. Chunks are accumulated to at least 200 ms before enqueueing to keep bridge traffic low, as recommended in https://www.callstack.com/blog/from-files-to-buffers-building-real-time-audio-pipelines-in-react-native .
   - Turn taking is half duplex in v1: while Rétor speaks, `onAudioReady` frames are not sent (the recorder keeps running so the session never flips). Barge-in (user interrupts Rétor) is a Phase 8 option that depends on AEC working on both platforms (issue #1254 shows Android needs the output stream opened with `Usage::VoiceCommunication`, which 0.13.3 does not do).

4. Coexistence: since one library holds the session, switching between an attempt screen and the debate screen is `setAudioSessionActivity(false)`, new `setAudioSessionOptions`, `setAudioSessionActivity(true)`. No second audio library is allowed to call `AVAudioSession` or `AudioManager` on the phone.

## Consequences

- One native audio dependency with prebuilt binaries downloaded at `npm install` time (`scripts/download-prebuilt-binaries.sh`). EAS build workers must reach the download host; a failed download breaks the build (0.13.3 itself fixed "prebuilt binaries downloading").
- FFmpeg (LGPL 2.1+) ships in both binaries by default. If kept: add FFmpeg and WebKit notices to the in-app licences screen (G3) and keep the linking dynamic as shipped (xcframeworks on iOS, `.so` files on Android). If removed (`disableFFmpeg: true`): Android can only record WAV, so Android takes would be uploaded as 16 kHz mono 16-bit WAV (about 9.6 MB for 300 s against about 2.4 MB in AAC), the bucket path contract `{id}.m4a` in `docs/DATA-MODEL.md` and the storage policy would need a second allowed extension, and the worker would transcode. This trade-off is decided by checklist items 6 and 13, not here.
- `androidInputPreset: 'unprocessed'` waits for `react-native-audio-api` 1.0.0. Until then Android uses `voiceRecognition`, which on most devices means no AGC but is not guaranteed; the Phase 1 measurement (item 4) tells us whether the difference matters for `volume.*`.
- The iOS interruption bug #1220 means that, on 0.13.x, resuming capture after a phone call may need an engine rebuild from JavaScript (stop the recorder, deactivate and reactivate the session, start again). Our "end the take on interruption" rule sidesteps it for attempts; the debate must handle it explicitly (item 5 and 9).
- Because the recorder writes M4A with the `moov` atom at the end, a take killed mid-way is lost on both platforms. The product already has states for this (annulée in the local queue, X-states in the mockup). No recovery code is written for it.
- Praat and `packages/moteur` receive 16 kHz mono PCM decoded by ffmpeg in the worker image, so the phone format can change (WAV or M4A, 16 or 48 kHz) without touching the engine.
- If `react-native-audio-api` cannot build or run on SDK 57 (checklist item 1), the fallback is: attempts on `expo-audio` 57.0.4 `AudioRecorder` with `{ extension: '.m4a', sampleRate: 16000, numberOfChannels: 1, bitRate: 64000, android: { outputFormat: 'mpeg4', audioEncoder: 'aac', audioSource: 'unprocessed' }, ios: { outputFormat: IOSOutputFormat.MPEG4AAC, audioQuality: AudioQuality.HIGH } }`, plus a 30-line local Expo module (`apps/mobile/modules/session-mesure`) exposing one function that calls `AVAudioSession.sharedInstance().setCategory(.playAndRecord, mode: .measurement)` after `prepareToRecordAsync` and before `record()`; and the debate on `@mykin-ai/expo-audio-stream` 0.3.5 (16 kHz PCM in and out) with the risk of a small maintainer, or on `expo-audio` `useAudioStream` for the uplink with strictly half-duplex playback through `AudioPlayer` on temporary WAV files (worse latency). A custom Expo module for both directions is the last resort.

## Verification checklist (Phase 1, real devices: one iPhone, one mid-range Android on Android 14 or newer)

1. Build: `react-native-audio-api@0.13.3` compiles and runs in an SDK 57 development build (React Native 0.86.3, New Architecture) on iOS (local `npx expo run:ios`) and Android (EAS development build), with the config plugin applied by CNG. Record the exact `react-native` version the SDK 57 template pins and reconcile it with the plan's "0.87".
2. Config: `iosMicrophonePermission` produces `NSMicrophoneUsageDescription`; Android manifest has `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MICROPHONE` and a service with `foregroundServiceType="microphone"`; the permission prompt and the denied path (X-state) behave.
3. iOS measurement mode: record the same 30 s speech at 30 cm and at 1 m with `iosMode: 'measurement'` and with `'default'`; on the server, plot the RMS envelope of both files; confirm that `measurement` shows no gain pumping and a larger dynamic range. Also confirm the mode is really applied (`AVAudioSession.sharedInstance().mode` read from a debug native call, or from the Xcode console).
4. Android input: same comparison with the 0.13.3 default (`voiceRecognition`) and, on a nightly build, `androidInputPreset: 'unprocessed'`; check `AudioManager.getProperty(PROPERTY_SUPPORT_AUDIO_SOURCE_UNPROCESSED)` on the test device. Decide whether waiting for 1.0.0 matters.
5. Interruptions: incoming phone call, then alarm, then Siri or Google Assistant, during a 90 s take on both platforms; expected: `observeAudioInterruptions` fires `began`, the take ends, the file is playable with `ffprobe`, the queue state is `annulée` or `en attente réseau` as designed, and the app can start a new take without a restart (issue #1220 regression test).
6. File output: `FileFormat.M4A` on iOS and Android (FFmpeg on) and `FileFormat.Wav` on Android (FFmpeg off) for a 300 s take; verify with `ffprobe` sample rate 16000, one channel, duration within 1 percent, and file sizes; measure the Android binary size with and without FFmpeg; decide FFmpeg on or off and update `docs/DATA-MODEL.md` if WAV wins.
7. App kill: swipe the app away and force stop from settings during a take on Android, and swipe away on iOS; expected: the file is missing or unplayable, the local queue deletes it on next launch, nothing is uploaded, no crash.
8. Background: lock the screen during a 5 min take on both platforms; expected: recording continues, the Android notification is visible, the duration matches.
9. Routes: plug wired earphones, then connect a Bluetooth headset mid-take; expected with `allowBluetoothHFP` omitted: the take stays on the built-in microphone; record what happens to the sample rate and whether `AVAudioEngineConfigurationChangeNotification` kills the engine (issue #1209).
